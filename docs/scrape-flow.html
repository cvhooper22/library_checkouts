Checkout Scrape Flow

A scrape is one function with three ways to start it. Here is how the Re-stamp button reaches a library site through GitHub Actions, how the nightly run picks its accounts, and where each switch sits.

Where this stands

The run script and the API's dispatch call are tested locally, with GitHub stubbed. The workflow itself hasn't run on GitHub yet. A first manual run will settle the two open questions: whether Chrome's sandbox starts on the runner, and whether the library site accepts GitHub's IP addresses.

One function, three triggers

Everything that scrapes ends in runScrape(), so decryption, validation and what gets written never depend on who started it.

On demand: the Re-stamp button

The frontend never waits on the scrape. It gets a run id back at step 5, then polls that run's row while the runner does the work.

Re-stamp is enabled only when GET /features reports refresh: true, which is REFRESH_ENABLED=true on the API. If SCRAPE_BACKEND is unset, step 4 becomes a BullMQ queue.add and steps 8–12 happen in the always-on worker instead. Nothing else changes.

Scheduled: nightly, for chosen households

No API involved. GitHub's clock starts the workflow, and the script decides which accounts to scrape from one repo variable.

Where each switch lives

Four places hold configuration. Only the API's is changed on Render.
