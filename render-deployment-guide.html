1 Prep your repo structure

Render deploys from a Git repo, and each Render service can point at a subdirectory. A monorepo with clear boundaries makes the next steps painless.

Lay out the folders

A structure like this maps cleanly onto four Render services (API, worker, cron, static frontend):

your-repo/
  api/              # small Express/Fastify app — read endpoints + /refresh
    package.json
    src/
  worker/           # BullMQ worker, scraper registry, Puppeteer
    package.json
    scripts/
      reseed-demo.js     # separate cron: regenerates demo data, never enqueues
    src/
      enqueueDaily.js    # daily cron: enqueues real accounts only
      scrapers/
        index.js
        bibliocommons.js
        koha.js
        demo.js          # synthetic data — called only by reseed-demo.js
  frontend/         # static site (Vite/React/etc.)
    package.json
    src/
  db/
    migrations/
  render.yaml       # optional: define all services as code

Add a Dockerfile to the worker (Puppeteer needs system deps)

Render's default Node buildpack won't have Chromium's system libraries. Use a Dockerfile for the worker service specifically:

FROM node:20-slim

RUN apt-get update && apt-get install -y \
    chromium \
    fonts-liberation libnss3 libatk-bridge2.0-0 libgtk-3-0 \
    libxss1 libasound2 --no-install-recommends \
    && rm -rf /var/lib/apt/lists/*

ENV PUPPETEER_SKIP_CHROMIUM_DOWNLOAD=true \
    PUPPETEER_EXECUTABLE_PATH=/usr/bin/chromium

WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY . .
CMD ["node", "src/index.js"]

The API and frontend don't need Chromium — they can use Render's native Node/static buildpacks with no Dockerfile.

Push to GitHub (or GitLab)

Render connects directly to a Git provider and redeploys on push. Commit the structure above and push before moving to Render itself.

2 Create a Render account & workspace

One workspace holds all your services, databases, and shared env vars for this project.

Sign up and connect Git

Go to render.com, sign up (GitHub OAuth is the fastest path since it also grants repo access), and authorize Render to see your repo. No credit card required to start on the Hobby (free) plan.

Create a new workspace/project

From the dashboard, start a new Project and give it a name (e.g. library-tracker). Every service you add below goes into this project so they share private networking and are easy to find together.

3 Provision Postgres

This is your source of truth: accounts, households, checkouts, runs.

Add a Postgres instance

In your project, click New → PostgreSQL. Choose a name (library-tracker-db), region (pick the same region you'll use for your other services — cuts latency and keeps traffic on Render's private network), and the free/starter plan to begin with.

Save the connection string

Once provisioned, Render shows an Internal Database URL (for services inside the same project — use this) and an External Database URL (for connecting from your laptop, e.g. via psql or a migration tool). Copy both somewhere safe.

Run your schema migrations

Migrations are Prisma migrations in db/prisma/migrations/, and db/package.json already has a migrate:deploy script. From your local machine, run it against the External Database URL:

cd db
DATABASE_URL="<external-url>?sslmode=require" npm run migrate:deploy

A successful run ends with "All migrations have been successfully applied." Running it again is safe — it reports nothing to apply. Re-run it whenever you add a migration.

  • Use the External URL, not the Internal one. The Internal URL only resolves from inside Render's network, so it won't work from your laptop.
  • SSL is required. If the URL you copied has no ?sslmode=require, add it.
  • Use migrate:deploy, never migrate:dev, against this database. deploy only applies committed migrations; dev can generate new migrations or reset the database.
  • Shell history: the password ends up in your history. Put a leading space before the command (zsh usually skips those) or export the variable in a throwaway shell.
  • Seeding is optional. npm run seed in db/ creates a dev user (dev@example.com) and two placeholder libraries — not demo checkouts. Check what prisma/seed.js inserts before running it against a real database.

4 Provision Redis (Key Value)

BullMQ needs Redis to hold the job queue between the API (which enqueues jobs) and the worker (which processes them).

Add a Key Value instance

Click New → Key Value in your project. Same region as Postgres and your services. Note the internal connection URL it gives you — this becomes REDIS_URL for both the API and worker services.

5 Deploy the API service

This is the small backend that the frontend talks to: read endpoints for checkouts, and the /refresh endpoint for on-demand scrapes.

Create a new Web Service

New → Web Service, select your repo, and set:

FieldValue
Root Directoryapi
EnvironmentNode
Build Commandcd ../db && npm install --include=dev && npx prisma generate && cd ../api && npm install
Start Commandnode src/index.js
PlanFree (or Starter, $7/mo, if you want no cold-start sleep)

Root Directory is api, not api/src. It's the folder Render runs your build and start commands from, and it must contain package.json. The start command node src/index.js is relative to it.

Why the build command reaches into db/

api/package.json depends on the sibling package "@library-tracker/db": "file:../db". Render clones the whole repo, so ../db is available to a native Node service, but a plain npm install in api doesn't install db's own dependencies or generate the Prisma client. Without those, the API crashes at startup on require('@library-tracker/db').

  • prisma generate is a different job from migrations. Migrations change the database (already done in Phase 3). generate reads db/prisma/schema.prisma and writes the PrismaClient code into node_modules. Render builds from a fresh checkout with no node_modules, so this has to happen in every build; without it, new PrismaClient() throws "did not initialize yet. Please run prisma generate".
  • --include=dev is needed because Render sets NODE_ENV=production, which would otherwise skip prisma (a devDependency) — the CLI that generate needs.
  • If the build can't see ../db, the fallback is a Dockerfile for the API with the repo root as the build context, like the worker's.

Note the assigned URL

Render gives this service a URL like library-tracker-api.onrender.com — this is what your frontend will call, and what you'll eventually point a custom domain at.

6 Deploy the background worker

This is the always-listening process that pulls scrape jobs off the queue and runs Puppeteer.

Create a new Background Worker

New → Background Worker, select the same repo, and set:

FieldValue
Root Directoryworker
EnvironmentDocker (uses the Dockerfile from Phase 1)
PlanStarter, $7/mo minimum — Puppeteer needs real memory, avoid the free tier here
Memory: headless Chrome typically needs 512MB–1GB per concurrent scrape. If you're running several accounts' scrapes in parallel, size the instance accordingly or cap BullMQ's concurrency to 1–2.

Confirm it connects to Redis and Postgres

Once deployed, check the service logs for a successful Redis connection and a successful DB connection on boot — this confirms the env vars from Phase 9 are wired correctly.

7 Set up the cron job

This triggers the daily scrape by enqueueing jobs — it does not scrape directly itself.

Create a new Cron Job

New → Cron Job, same repo, root directory worker (it can reuse the same Docker image). Set:

FieldValue
Schedule0 6 * * * (6am UTC daily — adjust per timezone need)
Commandnode src/enqueueDaily.js

enqueueDaily.js queries all non-demo accounts and pushes one job per account onto the same BullMQ queue the worker listens to. It does not run Puppeteer itself — that stays in the worker.

Pricing note: Cron Jobs on Render run as a small billed line item (roughly $1/mo) separate from your worker's compute — cheap, but worth knowing it's not bundled into the worker's plan.

8 Set up the demo reseed cron job

Powers the "Try it out" login button with an always-fresh, shared demo household — without that traffic ever touching the BullMQ queue your real accounts share. See adr/0002-demo-mode.md for the full reasoning.

Create a second, independent Cron Job

New → Cron Job, same repo, root directory worker (reuses the same Docker image as Phases 6 and 7). Set:

FieldValue
Schedule0 */12 * * * (every 12 hours)
Commandnode scripts/reseed-demo.js

reseed-demo.js creates the demo user/household/accounts on first run, then fully replaces their runs/checkouts every time it runs, regenerating due dates relative to "today." It calls the demo scraper module directly, in-process — it never enqueues a BullMQ job.

Keep this a separate Cron Job — do not fold it into Phase 7's schedule or command. The whole point of demo mode is that a public, credential-less "Try it out" button can never reach the same queue your real accounts' scrapes go through. Merging the two schedules (or having one script do both) would undo that guarantee the moment either script changes.
Pricing note: this is a second billed Cron Job (~$1/mo), on top of Phase 7's. Cadence is a cosmetic choice, not a functional one — checkouts.due_date and overdue are static values written at reseed time (architecture.md §4), so the only cost of reseeding less often is demo data visibly aging between runs.

9 Deploy the frontend

A static site that calls your API service for data.

Create a new Static Site

New → Static Site, same repo, set:

FieldValue
Root Directoryfrontend
Build Commandnpm install && npm run build
Publish Directorybuild

The frontend is SvelteKit with adapter-static, which writes to build/ (plain Vite apps use dist).

Set VITE_API_URL here, pointing at your API service's Render URL from Phase 5 (e.g. https://library-tracker-api.onrender.com, no trailing slash). It's baked in at build time, so it must be set before the first build, and changing it later needs a redeploy — a restart won't pick it up.

Add a rewrite rule for client-side routes

The app is built as a single-page app (fallback: 'index.html'), so routes like /dashboard don't exist as files. Without a rewrite, refreshing or deep-linking to one returns a 404. In the static site's Redirects/Rewrites settings, add a Rewrite with source /* and destination /index.html.

10 Wire up environment variables

The API and the worker need the same DB, Redis, and encryption-key values. Render lets you set these once and reference them across services.

Set shared env vars on each service

VariableUsed byValue
DATABASE_URLAPI, Worker, both Cron JobsInternal Postgres URL from Phase 3

CREDENTIAL_ENCRYPTION_KEYAPI, Worker, both Cron JobsGenerated locally — see below. Must be the same value everywhere: the API encrypts credentials on write, the worker decrypts them at scrape time, and the demo reseed job encrypts a placeholder blob for its own accounts.

PORT is set by Render automatically; the API reads it, so don't set it yourself. On the API, DATABASE_URL, REDIS_URL, JWT_SECRET and CREDENTIAL_ENCRYPTION_KEY are required — the API fails without them. DEMO_MODE_ENABLED defaults to on when unset; only false turns it off. Render's environment groups let you define shared values (like REDIS_URL and CREDENTIAL_ENCRYPTION_KEY) once and attach them to several services.

Google sign-in (optional, not wired up in the frontend yet)

GOOGLE_CLIENT_ID is the public ID of an OAuth app you register with Google. The API uses it to check that a Google ID token sent to POST /auth/google was issued for your app. The frontend's "Continue with Google" button is currently disabled, so you can leave this unset — email/password and demo login work without it. When you're ready:

  1. In the Google Cloud Console, create a project (or pick one).
  2. APIs & Services → OAuth consent screen: choose External, fill in the app name and your email, and add yourself as a test user while in testing mode.
  3. Credentials → Create Credentials → OAuth client ID, type Web application.
  4. Under Authorized JavaScript origins, add your local dev origin (e.g. http://localhost:5173) and your deployed frontend URL — no trailing slash or path.
  5. Copy the Client ID (…apps.googleusercontent.com) and set it as GOOGLE_CLIENT_ID on the API.

The Client ID isn't secret, and sign-in alone doesn't need the Client Secret (the API only verifies ID tokens). The frontend will need the same ID when the button is wired up, probably as a build-time VITE_GOOGLE_CLIENT_ID.

Google Calendar reminders (optional)

A household member can connect their Google Calendar from the Set up page. The app creates a "Library Due Dates" calendar in their account and keeps one reminder event on it, on the soonest due date. It uses the same OAuth client as sign-in, plus its secret:

  1. In the same Cloud project, enable the Google Calendar API (APIs & Services → Library).
  2. Under Google Auth Platform → Data Access, add the scope https://www.googleapis.com/auth/calendar.app.created. It only reaches calendars the app itself creates, and Google rates it non-sensitive.
  3. On the web client, add Authorized redirect URIs for http://localhost:5173/calendar/callback and your deployed frontend's /calendar/callback, and create a client secret.
  4. While the app is in Testing, add each person who will connect as a test user. Testing-mode grants expire after 7 days; the Set up page then shows a "reconnect" message.
  5. Set GOOGLE_CLIENT_SECRET, GOOGLE_CALENDAR_REDIRECT_URI and CALENDAR_ENABLED=true on the API, and GOOGLE_CLIENT_ID / GOOGLE_CLIENT_SECRET wherever calendars are synced (below).

Calendars are written only by the worker side, never the API: after every scrape, after a settings change or disconnect, and once a day to keep overdue reminders on today. With the BullMQ setup, add a third Cron Job (root worker, command npm run sync-calendars, schedule 0 12 * * * — about 5 AM Pacific, ahead of the default 8 AM reminder) with DATABASE_URL, CREDENTIAL_ENCRYPTION_KEY, GOOGLE_CLIENT_ID and GOOGLE_CLIENT_SECRET. With SCRAPE_BACKEND=github, .github/workflows/calendar-sync.yml does this instead: add GOOGLE_CLIENT_ID and GOOGLE_CLIENT_SECRET as repo secrets, and note that GitHub only dispatches workflows that exist on the default branch.

Generate a credential encryption key and a JWT secret

Locally, generate each as a strong random value and paste them into Render's dashboard as secrets (never commit either to the repo):

openssl rand -base64 32   # CREDENTIAL_ENCRYPTION_KEY
openssl rand -base64 32   # JWT_SECRET
Keep secrets out of render.yaml if you commit that file to Git. Set values marked as secrets directly in the Render dashboard, or use sync: false in render.yaml so Render prompts for them instead of storing them in the repo.

11 Add your custom domain

Free on Render's Hobby plan (two domains included) and Pro plan (25 included, then $0.25/mo each).

Add the domain to the frontend service

Open the Static Site → Settings → Custom Domains → Add Custom Domain. Enter e.g. app.yourdomain.com.

Point DNS at Render

At your domain registrar, add the CNAME record Render shows you (typically pointing at your onrender.com hostname). For an apex domain, Render supports ALIAS/ANAME records or gives you an IP for an A record depending on your registrar's capabilities.

Do the same for the API, on a subdomain

e.g. api.yourdomain.com → your API service. Update VITE_API_URL on the frontend to use this instead of the raw onrender.com URL, then redeploy the frontend.

Wait for verification and SSL

Render auto-issues and renews a TLS certificate once DNS propagates — usually minutes, occasionally up to a few hours. The dashboard shows a green check when it's live.

12 Test the full round trip

Confirm every piece talks to every other piece before you trust the daily cron.

Seed one test account

Insert a row into accounts (via the external Postgres URL) with real credentials for one library card, and a valid scraper_type.

Trigger an on-demand refresh

curl -X POST https://api.yourdomain.com/accounts/<account-id>/refresh \
  -H "Authorization: Bearer <your-login-token>"

Watch the worker's logs in the Render dashboard — you should see the job picked up, Puppeteer launch, and a run recorded as success or failed with a reason.

Confirm the frontend reflects it

Load app.yourdomain.com and confirm the checkout list appears and matches what the worker wrote to Postgres.

Manually trigger the cron job once

From the Cron Job's page in the dashboard, use Trigger Run to fire it outside its schedule and confirm it enqueues jobs for every due account, not just your test one.

Confirm demo mode works — and is actually read-only

Trigger Phase 8's Cron Job once manually, then check that a demo login returns data and can't mutate anything:

curl -X POST https://api.yourdomain.com/auth/demo
# -> { "token": "...", "householdId": "..." }

curl https://api.yourdomain.com/households/<householdId>/checkouts \
  -H "Authorization: Bearer <token>"
# -> populated checkout list

curl -X POST https://api.yourdomain.com/accounts/<demo-account-id>/refresh \
  -H "Authorization: Bearer <token>"
# -> 403, "The demo account is read-only."

That last 403 is the important one — it's confirming the demo token can never reach the BullMQ queue, not just that the feature "looks read-only" in a UI you haven't built yet.

13 Ongoing operations

A few habits that will save you time once this is running unattended.

Watch the free-tier sleep behavior

If the API is on the free plan, it spins down after 15 minutes of inactivity and takes 30–60 seconds to wake on the next request. Fine for a personal dashboard; upgrade to Starter ($7/mo) once other people depend on it responding instantly.

Set up basic alerting

Render can notify you (email/Slack) on deploy failures. Pair this with checking your own runs table periodically for a run of consecutive failed statuses on any one account — that's usually a sign a library changed their site markup and a scraper needs updating.

Redeploys are automatic

Every push to your connected branch triggers a rebuild and redeploy of the affected service(s). No manual step needed after the initial setup above.

Quick checklist

  • Repo split into api/, worker/, frontend/, with a Dockerfile for the worker
  • Postgres provisioned, migrations run
  • Redis (Key Value) provisioned
  • API deployed as a Web Service
  • Worker deployed as a Background Worker (Starter plan or above)
  • Cron Job deployed, enqueues rather than scrapes directly
  • A second, independent Cron Job deployed for reseed-demo.js — never sharing a schedule or command with the enqueue cron
  • Frontend deployed as a Static Site, pointed at the API URL
  • Shared env vars (DATABASE_URL, REDIS_URL, encryption key, JWT_SECRET, DEMO_MODE_ENABLED) set on every relevant service
  • If using calendar reminders: Calendar API enabled, calendar.app.created scope and /calendar/callback redirect URIs on the client, Google env vars set, and a daily sync-calendars run (Cron Job or calendar-sync.yml)
  • Custom domain attached to frontend and API, DNS verified, SSL live
  • One account tested end-to-end: seed → refresh → worker logs → frontend display
  • Demo mode tested: /auth/demo returns a token, checkouts load, and /refresh returns 403 for that token
